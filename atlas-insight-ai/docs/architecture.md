# Architecture

Atlas Insight AI is a multi-tenant B2B analytics SaaS built as a single
Next.js application (App Router) with Supabase (PostgreSQL + Auth + Storage)
as the platform layer. The strategic core is the pipeline:

```
DATA PLATFORM → SEMANTIC LAYER → BUSINESS KNOWLEDGE → METRICS ENGINE
             → AI ORCHESTRATOR → QUERY ENGINE → DASHBOARD ENGINE → AI ANALYST
```

## Module map

| Directory | Responsibility |
|---|---|
| `src/app` | Routes only — pages and API route handlers. Thin; delegates to services. |
| `src/components` | Design system (`ui/`) and layout chrome (`layout/`). |
| `src/features` | Client-side feature components (dialogs, views) per domain. |
| `src/connectors` | `DataConnector` interface + one adapter per source (Postgres, SQL Server, BigQuery, Files). |
| `src/data-profiler` | Pure profiling + relationship-detection logic. |
| `src/semantic` | Semantic model schema (Zod) and generator. |
| `src/metrics` | Metric formula language: parser, validator, SQL compiler. |
| `src/business-rules` | (rules live in DB; parsing is in `src/ai`) |
| `src/dashboards` | Dashboard specification schema + chart renderer. |
| `src/ai` | LLM abstraction, prompt templates, workspace context builder, orchestrator, SQL validator. |
| `src/services` | Server-side domain services: auth context, data sources, ingestion, profiling, query engine, dashboards, credentials. |
| `src/lib` | Supabase clients, env validation, crypto, utilities. |
| `src/types` | Shared domain types (mirror of the DB schema). |
| `supabase/migrations` | Full SQL schema, RLS policies, storage buckets, file query engine. |
| `tests` | Vitest unit tests + Playwright E2E. |

## Request flow (AI analysis)

1. `POST /api/ai/chat` → `requireWorkspace()` authenticates and checks the
   caller's role for the workspace (RBAC), on top of RLS.
2. `AIOrchestrator` builds the structured context (certified metrics →
   business rules → semantic model → glossary) — never credentials.
3. The LLM produces intent + SQL (JSON). `validateReadOnlySql` (AST-based)
   enforces read-only + single statement + table allowlist.
4. `executeQuery` runs it through the connector with timeout + row cap and
   records a `query_executions` row — the evidence id returned with every
   answer.
5. On execution errors the orchestrator feeds the error back to the LLM for
   repair (max 3 attempts, no infinite loop).
6. A second LLM call interprets the results; the answer carries highlights,
   insights, an optional chart and the full evidence block.

## Multi-tenancy

`User → Organization → Workspace → Resources`. Membership and role live in
`organization_members`; every resource table carries `workspace_id` and is
protected by RLS policies generated by `app.apply_workspace_policies()`
(select: member; write: EDITOR+). The service-role client is used only for
credentials and the file query engine, always after `requireWorkspace()`.

## Background jobs

Heavy operations (profiling, sync, ingestion) run synchronously in route
handlers in the MVP but are isolated behind service functions
(`profileDataSource`, `syncDataSource`, `ingestParsedFile`) so they can be
moved to a worker/queue without touching callers. See `deployment.md`.
